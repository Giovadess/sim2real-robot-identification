## Official SDK2 checkout

The local `~/mujoco_dev/unitree_sdk2/example/b2/b2_stand_example.cpp` uses `unitree_go::msg::dds_::LowState_` and `LowCmd_` on `rt/lowstate` and `rt/lowcmd`. It initializes motor command mode to `0x0A` and uses B2's `MotionSwitcherClient` to check and release the motion service before commanding. The DLS Go2 HAL uses the `unitree_go` message family but initializes motors to `0x01` and releases mode during startup. Therefore, the Go2 HAL must not be treated as a verified B2 HAL. The SDK example does not establish the leg order expected by our 12-joint dataset; observe B2 state and verify indices before adapting a bridge.

Gamma's `~/gamma_zero_tienkgun/deployment/unitree_b2/sdk2/run.py` uses native `unitree_sdk2py` in conda env `gamma_unitree` (Python 3.11, CycloneDDS, no `rclpy` or `ros2` CLI). Its `b2_profile.py` maps SDK indices 0..11 as FR, FL, RR, RL, each hip/thigh/calf, into the policy's FL, FR, RL, RR order. Its vendored official **Python** B2 example uses motor mode `0x01`, while the official C++ B2 example uses `0x0A`; the difference remains unresolved. Do not claim that `0x0A` is the only valid B2 mode. `b2_state_probe.py` uses the native SDK2 subscriber only; it never constructs a command publisher or motion-switcher client.

For SysID, the model and dataset expect raw joint angles in FL, FR, RL, RR order with no Gamma policy sign flips. The SDK index permutation is therefore `[3,4,5, 0,1,2, 9,10,11, 6,7,8]`. The existing collector runs at 200 Hz; any B2 low-level command bridge should maintain the 500 Hz command heartbeat independently and validate this permutation, joint limits, gains, state freshness, and command-loss behavior before enabling motion. In hardware mode the current ROS collector starts an idle-position command after the first valid state; it needs an explicit arm gate before being used on B2.

The standalone `b2_collect_sdk2.py` uses native SDK2 instead of the ROS HAL. Its default mode is `excitation` at speed 0.3; `--preview` shows the joint ranges without DDS. Without `--preview`, it subscribes to `rt/lowstate`, waits for fresh finite state, runs the clearance preflight, and requires typed `REST B2` before creating a `rt/lowcmd` publisher. It then ramps to and holds the collector start pose at a commanded maximum of 0.10 rad/s; a separate `ARM B2` is required before the trajectory starts. On hardware, if a motion mode is active it separately requires `RELEASE B2` before calling `ReleaseMode`. It commands at 500 Hz, records at 200 Hz, and stops publishing on stale/invalid state or excessive joint velocity. Hardware files go to `datasets/b2/`; `--sim` requires `--interface lo --domain 1`, skips the motion switcher, and writes to `datasets/b2_sim/`. `b2_npz_to_pt.py` converts either recording to the existing `.pt` fit input using the `aliengo_pacc_deploy_ros2_env` Python. The SDK command path has not been exercised on hardware. Stopping low-level command publication can make the robot lose motor hold; keep its base securely supported and the operator at the stop control.

During the ramp and trajectory, pressing Enter in the collector terminal or `Ctrl+C` stops command publication and saves a partial recording when at least two samples were collected. This is a software abort, not an emergency stop: it does not command motor damping, and the B2's response to loss of low-level commands has not been verified. Do not rely on the joystick to override a running low-level trajectory. Establish an independent physical stop procedure with the robot secured in the rig before commanding motion.

`--rig-check` is a separate, slower clearance motion for the selected planned trajectory (default excitation, speed 0.3, seed 12). It computes each leg's lowest foot pose from the model over all planned samples. After `REST B2` ramps from measured state to the collector start pose at up to 0.10 rad/s, the rig-check moves to those four poses at a commanded maximum of 0.10 rad/s, holds for 8 s, and returns to the collector start pose. It stops if measured joint speed exceeds 0.5 rad/s or tracking error exceeds 0.3 rad, and prints the model's lowest foot height for the full rig-check path before arming. It uses the same typed arm and mode-release gates and the same software abort. These feedback thresholds stop publication; they do not guarantee physical deceleration or damping. Preview without DDS: `~/miniforge3/envs/gamma_unitree/bin/python b2_collect_sdk2.py --rig-check --preview`.

All hardware motion now requires `--rest-foot-clearance METERS`: the measured floor gap under the lowest foot with the robot resting on its secured rig. Before the arm prompt or command publisher, the collector compares that gap to the model's maximum additional foot descent over the reset ramp and planned motion, and refuses if its predicted minimum is below `--min-clearance` (default and minimum 0.15 m). The height of the rig top alone is insufficient because the base origin and foot positions depend on how the B2 is mounted. This is a model-based floor preflight, not a guarantee; allow for rig deflection and measurement error, and separately ensure the feet cannot strike any part of the rig. For a 0.35 m measured resting gap, for example, use `--rest-foot-clearance 0.35` (not the stand height). The full excitation and rig check both use this gate.
